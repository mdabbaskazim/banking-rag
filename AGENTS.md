# AGENTS.md — Banking RAG Project Rules

## 1. Project Context

- Project: Banking RAG
- Python: 3.12
- Environment and dependencies: `uv`
- API: FastAPI
- Database: Neon PostgreSQL
- ORM and migrations: SQLAlchemy 2.x and Alembic
- PDFs: Local files in `Bank_pdf/`
- Development environment: Windows and PowerShell
- Architecture specification: `ARCHITECTURE.md`
- Progress tracking: `PROGRESS.md`

## 2. Source of Truth

- `ARCHITECTURE.md` is authoritative for architecture, schemas, security, implementation requirements, and phase boundaries.
- `PROGRESS.md` records completed work, actual test results, blockers, and the next phase.
- Existing working code and tests are the implementation baseline.
- If these sources conflict, identify the conflict before making a potentially breaking change.
- Never invent requirements that contradict the architecture.

## 3. Efficient Context Usage

- Do not reread the entire repository at the beginning of every task.
- Read `PROGRESS.md` first for current status.
- Read only the relevant sections of `ARCHITECTURE.md`.
- Inspect only the source files, tests, configuration, and migrations needed for the requested task.
- Reuse information already established in the current task.
- Do not repeatedly summarize files or produce lengthy plans.
- Do not inspect unrelated files unless debugging requires it.
- Avoid unnecessary dependency installation, version changes, refactoring, and generated output.
- Ask for clarification only when a missing detail materially blocks safe implementation.

## 4. Phase-Based Development

- Implement only the phase explicitly requested by the user.
- Do not start later phases or implement speculative features.
- Before editing, briefly state the intended changes.
- Implement incrementally using small, focused edits.
- Preserve existing functionality and public interfaces unless the architecture requires a change.
- Reuse existing utilities, configuration, provider interfaces, and testing patterns.
- Do not recreate working code from scratch.
- Stop after the requested phase and await user approval.

## 5. Coding Standards

- Use Python 3.12-compatible code and existing project conventions.
- Use `uv` for dependency and environment management.
- Follow Ruff linting and formatting rules.
- Maintain Pyright type correctness.
- Write meaningful tests for new behavior and regressions.
- Keep normal unit tests offline and independent of cloud credentials.
- Prefer dependency injection and existing provider interfaces.
- Handle errors explicitly; do not suppress failures merely to pass tests.
- Add dependencies only when necessary and compatible with the existing lockfile.

## 6. Security and Credentials

- Never print, expose, or commit `.env` contents, API keys, database URLs, passwords, or tokens.
- Keep `.env` ignored by Git.
- Keep `.env.example` limited to safe placeholders.
- Never include secrets in logs, test output, exception messages, or documentation.
- Do not perform destructive database operations without explicit approval.
- Confirm the database target is a development environment before applying migrations.
- Never claim a cloud operation succeeded without verifying the result.

## 7. Local Banking PDFs

- Original PDFs remain on the user's PC in `Bank_pdf/`.
- Do not upload them to cloud storage or GitHub without explicit approval.
- Do not delete, move, or rewrite the PDFs.
- Check whether the directory is already tracked before changing Git ignore rules.
- Do not rewrite Git history or remove committed files without explicit approval.
- Keep document identifiers independent of machine-specific absolute paths.

## 8. Testing and Validation

- Inspect `pyproject.toml` to determine the actual configured quality-check commands when needed.
- Run the project's quality checks after implementation.
- Prefer focused tests while fixing individual failures.
- Avoid duplicate full test runs when a previous run is still active.
- If a command hangs, inspect its status and last output before starting another run.
- Report commands actually executed and their real results.
- Distinguish verified results from assumptions and untested operations.
- Never fabricate test results or counts.

## 9. Database and Migration Rules

- Follow the schema and migration requirements in `ARCHITECTURE.md`.
- Preserve existing migration history.
- Review autogenerated migrations before applying them.
- Avoid destructive or unrelated schema changes.
- Keep unit tests independent of a live Neon connection.
- Verify migration success against the intended development database before reporting it as applied.

## 10. Git Rules

- Never commit or push unless explicitly requested.
- Never force-push or rewrite history without explicit approval.
- Before a proposed commit, inspect `git status` and the staged diff.
- Exclude secrets, virtual environments, caches, generated artifacts, and unapproved PDFs.
- Do not stage everything blindly when sensitive or untracked files may exist.
- Preserve existing commits and unrelated user changes.

## 11. Completion Report

At the end of each phase, provide a concise report containing:

1. What was implemented.
2. Files created or modified.
3. Tests and commands actually run.
4. Actual pass/fail results.
5. Database or cloud operations genuinely verified.
6. Remaining work and blockers.
7. `PROGRESS.md` updates.
8. The next phase, without starting it.

Keep the report concise. Do not repeat the entire architecture or implementation plan.

## 12. Current Task Rule

The user's latest explicit request defines the task scope. If the user asks for Phase N, implement Phase N only, following the architecture and current progress record. Stop when that phase is complete and wait for approval.
